# SPEC-msdf-upgrade

**Status**: Implemented
**Priority**: P2 — visual quality improvement; no API break
**Depends on**: none
**Goal**: Replace the brute-force single-channel SDF generator with a proper MTSDF pipeline (msdf-atlas-gen), add 8 new font-specific and script-specific glyph sets, and update the shader to use the 4-channel MTSDF blend.

---

## Problem

All atlases generated by `tools/gen-atlas.html` are technically single-channel SDFs stored
as R=G=B. The generator computes a brute-force Euclidean distance transform in canvas 2D and
duplicates the result across all three channels. The shader already calls
`median3(s.r, s.g, s.b)` — the correct MSDF decode — but because R=G=B there is no
corner-preservation benefit; it degenerates to ordinary SDF.

True MSDF splits the glyph outline into three directional components (one per RGB channel).
At each pixel the median of the three channels recovers the distance while cancelling the
artefacts that affect any single channel in isolation — most visibly at sharp corners and
thin strokes. This matters for:

- **CRT telescreen mode** — glyphs rendered large and static; corner rounding is visible
- **Drip + edge-glow** — corona uses the SDF gradient; sharper edges produce tighter halos
- **POM normal field** — normals derived from SDF gradient become more accurate at corners

Additionally: the project has no glyph sets for Cyrillic, Japanese kana, or Chinese, and the
existing `latin`/`ascii` sets are rendered from an unspecified system font.

---

## MTSDF from day one — why not defer

MTSDF stores a conventional single-channel true SDF in the alpha channel alongside the
RGB MSDF data. The shader blends between the two based on on-screen texel density: at
large scale (CRT mode), MSDF is accurate at corners; at very small scale (rain mode,
glyphs 2–4 px wide), the true SDF in alpha is more stable against MSDF colour fringing.

The previous draft deferred MTSDF to a separate phase. That reasoning was wrong:
generating MTSDF is identical to generating MSDF except for a single `--type mtsdf` flag
passed to `msdf-atlas-gen`. The PNG format is the same (RGBA); the atlas layout is
identical. CRT mode is already shipping. There is no cost to doing it right from the start.
**This spec generates MTSDF for all new and regenerated atlases.**

---

## Goals

1. All new and regenerated atlases are true MTSDF (R≠G≠B in the MSDF channels; A = true SDF).
2. `sampleGlyph` blends MSDF ↔ true SDF based on screen-space glyph size with no API change.
3. Eight new glyph sets are defined in `glyph-sets.js` and wired into `CHAR_SETS` with correct `glyphCount`, `gridW`, `gridH`.
4. Each new set has a concrete font source; no font decision is left open.
5. All three demo HTML files (`matrix-3d.html`, `demo-crt.html`, `matrix-2d.html`) expose the new sets in their charset selects.
6. `data/fonts/` is gitignored; font extraction is documented in `tools/README.md`.
7. The `matrixcode_msdf.png` atlas continues to work without modification (backward-compatible MTSDF blend degrades silently on single-channel atlases).

---

## Non-Goals

- Replacing `matrixcode_msdf.png` (requires Matrix-Code.ttf which is not in-repo — tracked in Phase 3 as conditional).
- Splashscreen / particle-banner animation mode (separate future spec; reference data recorded in the Splashscreen Reference section below).
- Adding italic, bold, or stylistic variants of existing sets.

## Design

### MTSDF blend in `sampleGlyph`

The current function (lines 169–180 of `matrix-rain-tsl.js`):
```js
const sampleGlyph = Fn(([faceUV, gIdx]) => {
  const su  = select(frontFacing, faceUV.x, float(1).sub(faceUV.x));
  const col = mod(gIdx, uAtlasGridW);
  const row = floor(gIdx.div(uAtlasGridW));
  const atlasUV = vec2(
    col.add(su).div(uAtlasGridW),
    row.add(float(1).sub(faceUV.y)).div(uAtlasGridH),
  );
  const s = texture(atlasTexture, atlasUV).rgb;
  return median3(s.r, s.g, s.b);
});
```

**Updated signature** — add `blendSDF` as a third parameter:
```js
const sampleGlyph = Fn(([faceUV, gIdx, blendSDF]) => {
  const su      = select(frontFacing, faceUV.x, float(1).sub(faceUV.x));
  const col     = mod(gIdx, uAtlasGridW);
  const row     = floor(gIdx.div(uAtlasGridW));
  const atlasUV = vec2(
    col.add(su).div(uAtlasGridW),
    row.add(float(1).sub(faceUV.y)).div(uAtlasGridH),
  );
  const s    = texture(atlasTexture, atlasUV);      // full RGBA (not .rgb)
  const msdf = median3(s.r, s.g, s.b);
  return mix(msdf, s.a, blendSDF);
});
```

`blendSDF = 0` → pure MSDF (accurate corners, used at large scale / CRT).
`blendSDF = 1` → pure true SDF (alpha channel, stable at tiny scale / rain).
Values in between blend proportionally.

**`useSDF` computation — must be in uniform control flow:**

`sampleGlyph` is called inside the POM ray-march loop (potentially non-uniform control
flow). WGSL `dpdx`/`dpdy`/`fwidth` are only defined in uniform control flow. Calling
`fwidth` inside `sampleGlyph` would produce undefined behaviour in the loop context.

Fix: compute `useSDF` **once** in the `outputNode Fn` body, **before** the POM block, at
the initial (pre-march) cell UV:

```js
// In outputNode Fn, before the POM loop — uniform control flow
const screenPx = float(1).div(fwidth(initialFaceUV.x));
const useSDF   = smoothstep(float(6), float(3), screenPx);
```

Where `initialFaceUV` is the pre-POM cell UV already available in the `outputNode Fn`.

Semantics of `smoothstep(6, 3, screenPx)`:
- `screenPx` < 3 (tiny glyph, rain mode) → `useSDF = 1` → pure true SDF (no fringing)
- `screenPx` > 6 (large glyph, CRT mode) → `useSDF = 0` → pure MSDF (sharp corners)
- 3–6 px: smooth blend

**Call-site updates for the `blendSDF` parameter:**

All existing call sites must add the third argument:

| Call site | Context | `blendSDF` arg |
|---|---|---|
| POM march loop body | inside loop — non-uniform CF | `float(1)` (true SDF, stable) |
| POM binary refinement (3 calls) | inside loop | `float(1)` |
| Main mask: `sampleGlyph(finalFace, glyphIdx)` | after POM | `useSDF` |
| Normal field ×4 | after POM | `useSDF` |
| Chromatic aberration ×2 | after POM | `useSDF` |

**Backward compatibility with old single-channel atlases** (`matrixcode_msdf.png`):
For R=G=B, α=1 atlases (old format), `median3(r,g,b) = r = g = b` and `s.a = 1.0`, so
`mix(msdf, 1.0, useSDF)` returns values > 0.5 everywhere — i.e., the entire quad is
opaque. This breaks rendering. To handle this correctly: old single-channel atlases must
set `α = SDF value` (same as R/G/B), not `α = 1`. This is the case for MTSDF-generated
atlases where the alpha channel carries the true SDF. The `matrixcode_msdf.png` was
generated externally with unknown alpha content.

**Safe fallback**: detect single-channel atlases by checking if `s.r ≈ s.g ≈ s.b`. If
so, bypass the blend. This adds a per-sample branch. Alternatively, just note that
`matrixcode_msdf.png` must be verified to have correct alpha before this change ships.

**Revised backward-compat note**: The previous draft claimed "old single-channel atlases
produce `useSDF = 0` at rain scale anyway." This is wrong — `useSDF` depends on
`screenPx`, not on atlas content. At rain scale, `useSDF = 1`, so `mix(msdf, s.a, 1) =
s.a`. If `s.a = 1.0` (solid), all fragments pass the mask and the glyph renders as a solid
rectangle. This must be explicitly tested and resolved before shipping. Options:
A) Re-export `matrixcode_msdf.png` with proper MTSDF alpha (Phase 3).
B) Add a per-charSet shader flag `uAtlasMTSDF` (float 0/1) to bypass the alpha blend for
   legacy single-channel atlases — flip it off for `matrixcode` until Phase 3 is done.

**Decision: use option B.** Add `uAtlasMTSDF` uniform (default 1.0 for new atlases).
`setCharSet()` sets it to 0.0 when loading `matrixcode`. Updated blend:
```js
return mix(msdf, mix(msdf, s.a, blendSDF), uAtlasMTSDF);
```
When `uAtlasMTSDF = 0`: returns `msdf` regardless of `blendSDF`.
When `uAtlasMTSDF = 1`: returns the blended value.

### `msdf-atlas-gen` invocation

The `msdf-atlas-gen` npm package is a WebAssembly module with a JavaScript API, not a
CLI binary. The CLI tool is the `msdf-atlas-gen` C++ binary from the msdfgen project.

For the Node.js CLI tool, use the **`msdf-atlas-gen` npm package** JavaScript API:

```js
import MsdfAtlasGen from 'msdf-atlas-gen';  // WASM module
const gen = await MsdfAtlasGen();
// gen.generateMTSDF({ font, charset, ... })
```

The exact API surface must be verified against the installed package version before
implementation. If the WASM API is insufficient (e.g., no MTSDF support), fall back to
shelling out to the C++ binary via `child_process.execFile`.

### Runtime glyph weight tables

Two separate weight systems exist:

**1. `glyph-sets.js` `weights` array** — used only by the atlas generator tool (`gen-atlas-cli.js`)
to control rendering weight during per-glyph canvas rasterisation (font size scaling, stroke
emphasis). Not used at runtime.

**2. `GLYPH_WEIGHTS` in `matrix-rain-webgpu.js`** (line 83) — the runtime inverse-CDF LUT that
controls how frequently each glyph appears in the rain. `applyGlyphWeightLUT(charSet, ...)` looks
up `GLYPH_WEIGHTS[charSet]`. Unknown / unlisted sets → `null` → uniform sampling.

**3. `CHAR_SETS[key].weights` in `matrix-rain-2d-tsl.js`** — the 2D module's equivalent of
`GLYPH_WEIGHTS`. It is a local copy; the 2D module does not import from `matrix-rain-webgpu.js`.

For new sets, both `GLYPH_WEIGHTS` (3D) and `CHAR_SETS[key].weights` (2D) should be set to
`null` initially (uniform sampling). Sets where CJK/kana density matters (`cyber`, `japanese`,
`chinese`) can have weighted entries added in a follow-up, using the same per-glyph array format
as `matrix1999` in `matrix-rain-webgpu.js` lines 88–96.

## Design Decisions

| Decision | Chosen | Rejected | Reason |
|---|---|---|---|
| MTSDF vs MSDF for Phase 1 | MTSDF | MSDF-then-MTSDF | Identical generation cost (one flag); CRT mode already shipping; no benefit to intermediate step |
| `blendSDF` as parameter vs closure | Parameter | Closure variable | `sampleGlyph` is defined at module scope; per-fragment `toVar()` cannot be closed over at definition time |
| `fwidth` location | `outputNode Fn` body, pre-POM | Inside `sampleGlyph` | WGSL derivative ops require uniform control flow; POM loop is non-uniform |
| `uAtlasMTSDF` flag | Added | Silent detection | Detecting single-channel atlases per-sample adds cost; explicit flag is free and precise |
| Chinese script variant | Traditional (Noto Sans TC) | Simplified (Noto Sans SC) | Traditional forms have higher stroke density and produce richer POM relief |
| Noto font delivery | Direct TTF download | `@fontsource` npm packages | Fontsource packages ship WOFF2; `msdf-atlas-gen` requires TTF/OTF |
| New-set runtime weights | `null` (uniform) initially | Weighted entries now | Uniform sampling is correct for most new sets; CJK-heavy sets can be tuned post-launch |

## Test Plan

No automated GPU tests are possible (no headless WebGPU in Node). Verification is visual.

| Test | Steps | Pass criteria |
|---|---|---|
| MTSDF corner quality | Load `matrix-3d.html`; increase POM depth to max; disable phosphor decay; zoom browser to 200% | Glyph corners are sharp; no soft rounding visible vs old atlas |
| Edge-glow fidelity | Enable edge-glow slider; compare `matrixcode` vs a new MTSDF set at same settings | New sets show tighter, more defined corona |
| MTSDF blend at rain scale | Default settings, `matrix-3d.html` | No colour fringing on glyph edges; characters readable |
| MTSDF blend at CRT scale | Switch to `postProcessing: 'crt'`; zoom CRT telescreen panel | Characters sharp; no colour fringing at enlarged size |
| `matrixcode` backward compat | Load with `charSet: 'matrixcode'` | Renders identically to pre-upgrade; no solid-rectangle artefacts |
| All 8 new sets visible | Cycle through each new charSet in `#ctl-charset` | Each set displays distinct character forms; no missing/blank columns |
| `cyrillic` mixed case | Load `cyrillic` set | Both uppercase and lowercase Cyrillic visible in rain |
| `japanese` kana | Load `japanese` set | Hiragana and katakana both present; no kanji unless explicitly inserted |

| Unused slot zero-weight | Load `cyber` set; enable weighted glyphs to 1.0 | No blank/transparent cells appear in rain (weight 0.0 = never sampled) |

## Risk Assessment

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| `msdf-atlas-gen` WASM API lacks MTSDF support | Medium | High | Shell out to C++ binary; document required binary version in tools/README.md |
| Noto Sans JP missing half-width katakana (U+FF65–U+FF9F) for `matrix1999` regen | High | Medium | Verify before regen; if missing, keep existing `matrix1999_msdf.png` and regenerate only new sets |
| `matrixcode_msdf.png` alpha channel = 1.0 (not SDF) breaks mask | High | High | `uAtlasMTSDF = 0` flag bypasses alpha blend for `matrixcode`; explicitly tested in smoke test |
| TTF not available at expected path in `data/fonts/` | Medium | Medium | `gen-atlas-cli.js` validates font paths at startup and prints actionable error |
| `canvas` npm package unavailable in CI | Low | Low | Atlas generation is a local dev tool, not CI; add to `.npmignore` / docs scope |

## Splashscreen Animation Reference

The KUSH42/playground `ParticleBannerComponent` implements a p5.js particle animation:
floating dots connecting with lines to neighbours within 85 px. Out of scope for this spec.

Reference parameters for a future `postProcessing: 'splash'` mode:

| Parameter | Value |
|---|---|
| Particle count | `containerWidth / 10` |
| Connection threshold | 85 px |
| Connection line | `rgba(255,255,255,0.04)` |
| Background | `#0f0f0f` |
| Particle radius | 1–8 px (random) |
| x speed | ∈ [−1, 1] |
| y speed | ∈ [−0.75, 0.75] |
| Color | randomised RGBA within green/blue/red bounds |
